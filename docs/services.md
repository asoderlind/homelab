# Dell services

[← Overview](../README.md)

- `https://home.soderlind.dev` is a lightweight static index of the homelab apps.
- `https://jobs.soderlind.dev` routes to Shoku, deployed as the rootless Podman
  container from `ghcr.io/asoderlind/shoku:2.4.1`. Its SQLite state is persisted
  at `/var/lib/shoku`. CV and resume authoring remain separate from Shoku.
- The `shoku` GHCR package must be public for the server to pull anonymously.
  If it remains private, authenticate rootless Podman as `axel` to GHCR before
  deploying. Shoku requires a password and cookie-signing key. Create the
  declared age secret before evaluating or deploying the flake:

  ```sh
  cd hosts/dell/secrets
  EDITOR=vim agenix -e shoku-env.age -i ~/.ssh/id_ed25519
  ```

  Put these entries in the encrypted env file, using a strong password and a
  key generated by `openssl rand -base64 48`:

  ```ini
  SECRET_KEY=replace-with-generated-key
  SHOKU_PASSWORD=choose-a-strong-password
  ```

  Agenix decrypts it at runtime as `/run/agenix/shoku-env`, readable only by
  the rootless `axel` service user. Shoku has no other access controls, so the
  hostnames remain reachable only
  through the tailnet-protected nginx ingress.

## Nextcloud (drive.soderlind.dev)

First-time setup after the initial deploy:

1. **Admin password**: initial value comes from the `nextcloud-admin-pass`
   secret (used only at install time). Read it with
   `sudo cat /run/agenix/nextcloud-admin-pass`, log in as `admin`, change
   it in the UI if you like.
2. **Register the serverinfo token** (one-time; the Prometheus exporter
   authenticates with it, but Nextcloud stores its copy in the DB):

   ```sh
   sudo nextcloud-occ config:app:set serverinfo token \
     --value "$(sudo cat /run/agenix/nextcloud-serverinfo-token)"
   sudo systemctl restart prometheus-nextcloud-exporter
   ```

   Re-run both after rotating the `nextcloud-serverinfo-token` secret.
3. **Verify**:

   ```sh
   sudo nextcloud-occ status                                  # installed: true
   curl -s http://127.0.0.1:9205/metrics | grep nextcloud_up  # nextcloud_up 1
   sudo fail2ban-client status nextcloud                      # jail active
   ```

### Troubleshooting

- **Exporter reports "too many requests" / `nextcloud_up 0` with a correct
  token**: the serverinfo endpoint is brute-force protected. Failed auth
  attempts (e.g. from a stale token) lock out the source IP — which is the
  host's own tailscale IP, since the exporter probes via
  `https://drive.soderlind.dev` — for up to 12h. Check and reset:

  ```sh
  sudo nextcloud-occ security:bruteforce:attempts <host tailscale IP>
  sudo nextcloud-occ security:bruteforce:reset <host tailscale IP>
  ```

- **A tailnet device gets banned by fail2ban** (3 failed Nextcloud logins):

  ```sh
  sudo fail2ban-client set nextcloud unbanip <ip>
  ```

- **Major Nextcloud upgrades** are not automatic: bump `pkgs.nextcloudNN`
  in `hosts/dell/services/nextcloud.nix` one major version at a time and
  deploy.

## Actual Budget (actual.soderlind.dev)

No secrets in the repo: the server password is created in-app. **Set it by
visiting `https://actual.soderlind.dev` right after the first deploy** — an
unconfigured server accepts whatever password the first visitor picks, so
until then anyone on the tailnet could claim it.

## Kavita (kavita.soderlind.dev)

Manga/comic server. Same first-visit caveat as Actual: **register the
admin account at `https://kavita.soderlind.dev` right after the first
deploy** — until then anyone on the tailnet could claim it. Then add a
library in the admin UI pointing at `/mnt/backup/media/manga` (create the
directory first; the `kavita` user only needs read access, which the
media tree's default permissions provide). The only repo secret is
`kavita-token` (JWT signing key); rotating it just logs everyone out.

## Miniflux (rss.soderlind.dev)

RSS reader, adapted from the poseidon repo. The admin account is created
on first start from the `miniflux-admin-creds` agenix secret
(`agenix -d hosts/dell/secrets/miniflux-admin-creds.age` on the laptop shows it);
change the password in-app afterwards — the file is only read again if
the user table is ever empty. State is the local `miniflux` postgres
database, backed up via the nextcloud restic jobs (see [Backups](backups.md)).

## Open WebUI (chat.soderlind.dev)

Runs the prebuilt `ghcr.io/open-webui/open-webui:v0.13.4` image through
rootless Podman as `axel`, avoiding a local frontend build. Upgrades are manual:
change the pinned release tag in `hosts/dell/services/open-webui.nix`.

[Deploy Dell](deployment.md#deploying), then immediately visit
`https://chat.soderlind.dev` while connected to Tailscale. Create your account:
the first account becomes administrator, so any tailnet member could claim it
until you do. In **Admin Panel → Settings → Connections**, edit the OpenAI
connection, confirm the URL is `https://openrouter.ai/api/v1`, enter your
OpenRouter API key, and save. Select a model and send a test message.
Disable new signups in the admin settings after creating your account.

The key is stored in Open WebUI's persistent database, never in Nix source or
the Nix store. Admin connection settings persist across restarts and take
precedence over the initial environment defaults. State (including the key,
accounts, chats, and uploads) lives in `/var/lib/open-webui-container`; the existing restic
jobs do not back it up. Stop `podman-open-webui.service` before copying this directory
for a consistent manual backup, then start it again.

The earlier native service's `/var/lib/open-webui` directory, if present, is
retained but is not automatically migrated into the container.

Check the service on Dell with `sudo systemctl status podman-open-webui` and
`sudo journalctl -u podman-open-webui -n 50`. The backend binds only to
`127.0.0.1:8081`; access goes through the existing HTTPS proxy.

## Bunko (bunko.soderlind.dev)

Runs `ghcr.io/asoderlind/bunko:0.0.4` as one rootless Podman container. The
GitHub Actions publish workflow builds the image for Dell's `x86_64-linux`
architecture. SQLite and uploaded media persist under `/var/lib/bunko`.
Nginx terminates HTTPS using the existing `soderlind.dev` wildcard certificate.

Before the first deploy, create the missing encrypted runtime environment:

```sh
cd hosts/dell/secrets
EDITOR=vim agenix -e bunko-env.age -i ~/.ssh/id_ed25519
```

The file should contain a generated application key, for example:

```text
SECRET_KEY=<at-least-32-random-characters>
```

No inference provider is configured in Nix. After deploying, create the initial
user interactively, then add OpenRouter from the Bunko **Settings** page using
`https://openrouter.ai/api/v1`, a model name, and the API key. After deploying,
create the initial user interactively:

```sh
sudo -u axel env XDG_RUNTIME_DIR=/run/user/1000 \
  podman exec -it bunko python -m app.cli set-password --username axel
```

Then visit `https://bunko.soderlind.dev`. Check the service with
`sudo systemctl status podman-bunko` and inspect logs with
`sudo journalctl -u podman-bunko -n 50`.

Bunko state is not yet included in the existing Restic jobs; add a consistent
SQLite backup after validating the initial deployment.

## Updating Bunko and Shoku releases

Both apps publish full-version image tags from Git tags (`vX.Y.Z` → `:X.Y.Z`).
Wait for the app's publish workflow and GitHub release to succeed before changing
HomeLab; a changelog entry alone does not mean the image is available.

The configured release pins are Bunko **0.0.4** and Shoku **2.4.1** in:

- `hosts/dell/services/bunko.nix`: `ghcr.io/asoderlind/bunko:0.0.4`
- `hosts/dell/services/shoku.nix`: `ghcr.io/asoderlind/shoku:2.4.1`

Commit those changes and run the normal Dell NixOS rebuild/deployment. Check
`podman-bunko` and `podman-shoku` service status and logs afterward. Repeat with
the exact full version for later releases; avoid moving `main` or `latest` tags
for production. Confirm the pinned images have finished publishing before deploying.
Back up app data first: reverting an image pin does not revert database changes.

## Monitoring

Prometheus (`:9001`) + Alertmanager → Telegram. Alert rules live in
`hosts/dell/services/alertmanager.nix`; exporters and scrape jobs live in
each service's own module. Grafana at `grafana.soderlind.dev`.

The `node` scrape job currently includes Dell and Raspberry Pi 5. In Grafana's
provisioned **Node Exporter Full** dashboard, select the `node` job and the
`dell` or `rpi5` instance.
