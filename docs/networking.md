# Homelab networking

There are two separate concerns: how clients reach services through
tailnet-only ingress, and how Transmission reaches the internet through a
Proton VPN split tunnel. Nothing else on Dell uses the VPN.

## Ingress: tailnet-only

The LAN firewall exposes only SSH (port 22). Everything else rides on
`tailscale0` being a trusted interface (`modules/common/networking.nix`) — any
port a service listens on is reachable from the tailnet without being opened in
the firewall, and unreachable from anywhere else.

DNS and TLS sit on top of that:

- A wildcard record `*.soderlind.dev` in the Cloudflare zone (DNS-only / grey
  cloud) points at the host's Tailscale IP. Public resolvers hand out a
  `100.64.0.0/10` address that only tailnet members can route to.
- nginx terminates TLS for all subdomains with one wildcard certificate,
  renewed via ACME DNS-01. HTTP-01 cannot work because Let's Encrypt cannot
  reach a tailnet-only host. Individual hostnames stay out of public CT logs.
- The host's resolver is Tailscale MagicDNS (`100.100.100.100`). This matters
  for the VPN namespace below and for ACME; lego is pointed at `1.1.1.1`
  directly because MagicDNS's upstream can serve stale records.

### Adding a Dell service subdomain

1. All `*.soderlind.dev` names already resolve to Dell's Tailscale IP through
   the DNS-only Cloudflare wildcard and are covered by the wildcard
   certificate, so no per-service DNS or certificate work is normally needed.
2. Add an nginx vhost with `forceSSL = true; useACMEHost = "soderlind.dev";`.
   Do not use per-vhost `enableACME`, because HTTP-01 cannot reach a
   tailnet-only host.
3. Do not open firewall ports; `tailscale0` is a trusted interface.

## Egress: Proton VPN split tunnel for Transmission

The plumbing lives in `hosts/dell/services/protonvpn.nix`, while
`hosts/dell/services/transmission.nix` attaches the daemon. All Transmission
traffic goes through Proton VPN, and only Transmission does so. Tailscale,
ACME, restic to Hetzner, Nextcloud, and other host traffic keep using the normal
uplink.

```text
              tailnet                      internet
                 │                            │
  ┌──────────────┼────────────────────────────┼──────────────────┐
  │ init netns   ▼                            ▼                  │
  │          tailscale0                      eno1                │
  │              │                            ▲                  │
  │            nginx                          │ encrypted UDP    │
  │              │ https → 10.233.0.2:9091    │ to Proton :51820 │
  │              ▼                            │                  │
  │         veth-trans ────┐             wg socket               │
  │         10.233.0.1     │            (stays here)             │
  └────────────────────────┼──────────────────┼──────────────────┘
                           │ veth pair        │ interface moved
  ┌────────────────────────┼──────────────────┼──────────────────┐
  │ netns "protonvpn"      ▼                  ▼                  │
  │                  veth-trans-ns       protonvpn (wg)          │
  │                  10.233.0.2          10.2.0.2/32             │
  │                        │                  ▲                  │
  │                        │ RPC              │ default route    │
  │                        ▼                  │                  │
  │                   transmission ── peers ──┘                  │
  │                        ▲                                     │
  │                   natpmp loop (renews forwarded port)        │
  └──────────────────────────────────────────────────────────────┘
```

How the pieces fit:

- **Namespace** (`protonvpn-netns.service`): a network namespace named
  `protonvpn`. Its routing table has exactly two entries: `10.233.0.0/24` on the
  veth and `default dev protonvpn` on the WireGuard interface. No fallback route
  exists, making this a structural kill switch: if the tunnel is down,
  Transmission has no egress path.
- **WireGuard** (`networking.wireguard.interfaces.protonvpn` with
  `interfaceNamespace`): the WireGuard link is created in the initial namespace,
  so its encrypted UDP socket uses the normal uplink, and then moved into the
  VPN namespace. There, `allowedIPs = 0.0.0.0/0` becomes the namespace's default
  route. The private key is the `protonvpn-wg-key` agenix secret; the server
  public key and endpoint are plain configuration in `protonvpn.nix`. Regenerate
  them at account.protonvpn.com if Proton retires the server, selecting a P2P
  server with NAT-PMP enabled.
- **Attachment**: `transmission.service` runs with
  `NetworkNamespacePath=/run/netns/protonvpn` and `bindsTo` the WireGuard unit,
  so it lives and dies with the tunnel.
- **Veth pair** (`veth-trans` at `10.233.0.1` and `veth-trans-ns` at
  `10.233.0.2`): this exists only so nginx can reach the RPC port inside the
  namespace. It carries no default route and is not a leak path. The RPC IP
  allowlist (`127.0.0.1,10.233.0.1`) restricts who may control the daemon.
- **DNS**: the host's `resolv.conf` points at MagicDNS, which is unreachable
  inside the namespace. `/etc/netns/protonvpn/resolv.conf` uses Proton's
  in-tunnel resolver at `10.2.0.1` for `ip netns exec` tooling. Transmission has
  the same file bind-mounted over `/etc/resolv.conf`, because systemd's
  `NetworkNamespacePath=` does not perform iproute2's `/etc/netns` swap.
- **Inbound peers** (`protonvpn-natpmp.service`): Proton assigns a random
  forwarded port through NAT-PMP. Mappings expire after 60 seconds, so a loop
  continuously renews UDP and TCP and updates Transmission's peer port when the
  assignment changes. The host firewall consequently has no open peer port;
  inbound peer traffic arrives through the tunnel.

## Verification

These checks are also useful after reboots or Proton server changes:

```sh
curl -s ifconfig.me                                        # home IP
sudo ip netns exec protonvpn curl -s ifconfig.me           # Proton IP
sudo ip netns exec protonvpn wg show                       # recent handshake
journalctl -u protonvpn-natpmp -n 5                        # forwarded port set
sudo systemctl stop wireguard-protonvpn                    # kill-switch test:
sudo ip netns exec protonvpn curl --max-time 5 ifconfig.me # ...times out
sudo systemctl start wireguard-protonvpn                   # transmission returns
```
