# nixos-homelab-dell

NixOS configuration for the Dell homelab. Services are tailnet-only: nginx
terminates TLS with a wildcard `*.soderlind.dev` cert (ACME DNS-01 via
Cloudflare) and nothing but SSH is exposed outside `tailscale0`.

Most things are declarative, but a few steps are manual. This is the list.

## Hardware

The Dell runs everything (NixOS + all services); the two Raspberry Pis are
separate Debian machines scraped as extra `node` targets by Prometheus (see
`modules/core/services/prometheus.nix`).

| Instance | Machine | CPU | RAM | Storage | OS |
| --- | --- | --- | --- | --- | --- |
| `dell` | Dell OptiPlex 3040 | Intel Core i5-6500T — 4C/4T, 2.5 GHz (Skylake) | 8 GB | 500 GB internal SATA HDD (Toshiba MQ01ACF050) | NixOS 26.05 |
| `rpi5` | Raspberry Pi 5 Model B (Rev 1.1) | Broadcom BCM2712 — quad Cortex-A76, 2.4 GHz | 16 GB | 32 GB microSD | Debian 12 (bookworm) |
| `rpi3` | Raspberry Pi 3 Model B (Rev 1.2) | Broadcom BCM2837 — quad Cortex-A53, 1.2 GHz | 1 GB | 16 GB microSD | Debian 13 (trixie) |

The `dell`/`rpi5`/`rpi3` names are the Prometheus `instance` labels.

**Backup HDD**: a Western Digital 2 TB USB drive (WD20EARX-00PASB0) mounted at
`/mnt/backup` on the Dell, holding the local restic repo (see
[Backups](#backups-restic--mntbackup)). Mounted `nofail`; the backup jobs check
the mountpoint and fail loudly if it's absent.

## Networking

Two separate concerns: how *we* reach services (tailnet-only ingress), and
how *Transmission* reaches the internet (Proton VPN split tunnel). Nothing
else on the host uses the VPN.

### Ingress: tailnet-only

The LAN firewall exposes only SSH (port 22). Everything else rides on
`tailscale0` being a trusted interface (`modules/core/networking.nix`) —
any port a service listens on is reachable from the tailnet without being
opened in the firewall, and unreachable from anywhere else.

DNS and TLS on top of that:

- A wildcard record `*.soderlind.dev` in the Cloudflare zone (DNS-only /
  grey cloud) points at the host's tailscale IP. Public resolvers hand out
  a `100.64.0.0/10` address that only tailnet members can route to.
- nginx terminates TLS for all subdomains with one wildcard cert, renewed
  via ACME DNS-01 (HTTP-01 can't work — Let's Encrypt can't reach a
  tailnet-only host). Individual hostnames stay out of the public CT logs.
- The host's own resolver is Tailscale MagicDNS (`100.100.100.100`). This
  matters for the VPN namespace below, and for ACME (lego is pointed at
  `1.1.1.1` directly because MagicDNS's upstream can serve stale records).

Current vhosts and their upstreams (all nginx → localhost, except
Transmission which lives in a network namespace):

| Subdomain | Upstream | Notes |
| --- | --- | --- |
| `grafana.soderlind.dev` | `127.0.0.1:2342` | websockets for live dashboards |
| `jellyfin.soderlind.dev` | `127.0.0.1:8096` | websockets for playback state |
| `drive.soderlind.dev` | php-fpm socket | vhost generated by the Nextcloud module |
| `habits.soderlind.dev` | `127.0.0.1:8080` | beaverhabits runs `--network=host` |
| `transmission.soderlind.dev` | `10.233.0.2:9091` | via veth into the VPN netns, see below |

Samba (media share) and the Prometheus/exporter ports follow the same
model: bound normally, reachable only over the tailnet.

### Egress: Proton VPN split tunnel for Transmission

Everything lives in `modules/core/services/protonvpn.nix` (plumbing) and
`transmission.nix` (attaching the daemon). The goal: **all** of
Transmission's traffic goes through Proton VPN, and **only** Transmission's
— Tailscale, ACME, restic → Hetzner, and Nextcloud keep using the normal
uplink.

```
              tailnet                      internet
                 │                            │
  ┌──────────────┼────────────────────────────┼──────────────────┐
  │ init netns   ▼                            ▼                  │
  │          tailscale0                      eno1                │
  │              │                            ▲                  │
  │            nginx                          │ encrypted UDP    │
  │              │ https → 10.233.0.2:9091    │ to Proton :51820 │
  │              ▼                            │                  │
  │         veth-trans ────┐             wg socket               │
  │         10.233.0.1     │            (stays here)             │
  └────────────────────────┼──────────────────┼──────────────────┘
                           │ veth pair        │ interface moved
  ┌────────────────────────┼──────────────────┼──────────────────┐
  │ netns "protonvpn"      ▼                  ▼                  │
  │                  veth-trans-ns       protonvpn (wg)          │
  │                  10.233.0.2          10.2.0.2/32             │
  │                        │                  ▲                  │
  │                        │ RPC              │ default route    │
  │                        ▼                  │                  │
  │                   transmission ── peers ──┘                  │
  │                        ▲                                     │
  │                   natpmp loop (renews forwarded port)        │
  └──────────────────────────────────────────────────────────────┘
```

How the pieces fit:

- **Namespace** (`protonvpn-netns.service`): a network namespace named
  `protonvpn`. Its routing table has exactly two entries: `10.233.0.0/24`
  on the veth, and `default dev protonvpn` (the WireGuard interface). No
  fallback route exists, which makes the setup a structural **kill
  switch**: if the tunnel is down, Transmission has no egress at all —
  there is nothing to leak through.
- **WireGuard** (`networking.wireguard.interfaces.protonvpn` with
  `interfaceNamespace`): the wg link is created in the init namespace —
  so its *encrypted* UDP socket egresses via the normal uplink — and then
  moved into the netns, where `allowedIPs = 0.0.0.0/0` becomes the
  namespace's default route. The private key is the `protonvpn-wg-key`
  agenix secret; server pubkey/endpoint are plain config in
  `protonvpn.nix` (regenerate at account.protonvpn.com if Proton retires
  the server — pick a **P2P** server with **NAT-PMP** enabled).
- **Attachment**: `transmission.service` runs with
  `NetworkNamespacePath=/run/netns/protonvpn` and `bindsTo` the wg unit —
  it lives and dies with the tunnel.
- **veth pair** (`veth-trans` 10.233.0.1 ↔ `veth-trans-ns` 10.233.0.2):
  exists only so nginx can reach the RPC port inside the namespace. It
  carries no default route, so it is not a leak path; the RPC IP
  whitelist (`127.0.0.1,10.233.0.1`) restricts who may drive the daemon.
- **DNS**: the host `resolv.conf` points at MagicDNS, which is
  unreachable from inside the namespace. `/etc/netns/protonvpn/resolv.conf`
  (Proton's in-tunnel resolver `10.2.0.1`) covers `ip netns exec` tooling;
  transmission gets the same file bind-mounted over `/etc/resolv.conf`
  because systemd's `NetworkNamespacePath=` does not perform iproute2's
  `/etc/netns` swap.
- **Inbound peers** (`protonvpn-natpmp.service`): Proton assigns a random
  forwarded port via NAT-PMP (paid plan); mappings expire after 60 s, so a
  loop renews UDP+TCP continuously and updates Transmission's peer port
  whenever the assignment changes. Consequently the host firewall has
  **no** open peer port — inbound peer traffic arrives through the tunnel.

Verify (also useful after reboots or Proton server changes):

```sh
curl -s ifconfig.me                                        # home IP
sudo ip netns exec protonvpn curl -s ifconfig.me           # Proton IP
sudo ip netns exec protonvpn wg show                       # recent handshake
journalctl -u protonvpn-natpmp -n 5                        # forwarded port set
sudo systemctl stop wireguard-protonvpn                    # kill-switch test:
sudo ip netns exec protonvpn curl --max-time 5 ifconfig.me # ...times out
sudo systemctl start wireguard-protonvpn                   # transmission returns
```

## Deploying

Always done manually, from the repo root:

```sh
nix run nixpkgs#deploy-rs -- .#nixos    # or `deploy .#nixos`
```

deploy-rs builds remotely on the host and auto-rolls-back if activation
fails (e.g. a unit fails to start during the switch). Validate before
deploying:

```sh
nix eval --raw .#nixosConfigurations.nixos.config.system.build.toplevel.drvPath
```

Note: flake eval only sees files known to git — `git add` new files
(including `.age` secrets) or they don't exist as far as nix is concerned.

## Secrets (agenix)

Recipients are defined in `secrets/secrets.nix` (server host key + laptop
key). To create or edit a secret, from `secrets/`:

```sh
EDITOR=vim agenix -e <name>.age -i ~/.ssh/id_ed25519
```

After editing, **verify the content is non-empty** — a scripted/failed
editor session can silently encrypt an empty string, which passes eval and
only blows up at activation time:

```sh
agenix -d <name>.age -i ~/.ssh/id_ed25519 | wc -c
```

On the host, decrypted secrets appear under `/run/agenix/<name>`.

## Adding a new service subdomain

1. All `*.soderlind.dev` names already resolve to the host's tailscale IP
   (wildcard record in the Cloudflare zone, DNS-only/grey cloud) and are
   covered by the wildcard cert — usually no DNS or cert work needed.
2. Add an nginx vhost with `forceSSL = true; useACMEHost = "soderlind.dev";`
   (never per-vhost `enableACME`: HTTP-01 can't reach a tailnet-only host).
3. Don't open firewall ports — `tailscale0` is a trusted interface.

## Nextcloud (drive.soderlind.dev)

First-time setup after the initial deploy:

1. **Admin password**: initial value comes from the `nextcloud-admin-pass`
   secret (used only at install time). Read it with
   `sudo cat /run/agenix/nextcloud-admin-pass`, log in as `admin`, change
   it in the UI if you like.
2. **Register the serverinfo token** (one-time; the Prometheus exporter
   authenticates with it, but Nextcloud stores its copy in the DB):

   ```sh
   sudo nextcloud-occ config:app:set serverinfo token \
     --value "$(sudo cat /run/agenix/nextcloud-serverinfo-token)"
   sudo systemctl restart prometheus-nextcloud-exporter
   ```

   Re-run both after rotating the `nextcloud-serverinfo-token` secret.
3. **Verify**:

   ```sh
   sudo nextcloud-occ status                                  # installed: true
   curl -s http://127.0.0.1:9205/metrics | grep nextcloud_up  # nextcloud_up 1
   sudo fail2ban-client status nextcloud                      # jail active
   ```

### Troubleshooting

- **Exporter reports "too many requests" / `nextcloud_up 0` with a correct
  token**: the serverinfo endpoint is brute-force protected. Failed auth
  attempts (e.g. from a stale token) lock out the source IP — which is the
  host's own tailscale IP, since the exporter probes via
  `https://drive.soderlind.dev` — for up to 12h. Check and reset:

  ```sh
  sudo nextcloud-occ security:bruteforce:attempts <host tailscale IP>
  sudo nextcloud-occ security:bruteforce:reset <host tailscale IP>
  ```

- **A tailnet device gets banned by fail2ban** (3 failed Nextcloud logins):

  ```sh
  sudo fail2ban-client set nextcloud unbanip <ip>
  ```

- **Major Nextcloud upgrades** are not automatic: bump `pkgs.nextcloudNN`
  in `modules/core/services/nextcloud.nix` one major version at a time and
  deploy.

## Backups (restic → /mnt/backup)

Daily (03:00, `Persistent` so missed runs catch up) restic backup of
`/var/lib/nextcloud` plus a fresh pg_dump
(`/var/backup/postgresql/nextcloud.sql.gz`) into the encrypted repo
`/mnt/backup/restic/nextcloud` on the external USB drive. Retention:
7 daily + 4 weekly + 6 monthly snapshots (up to 17, ~6 months of
coverage), pruned and checked after each run.

A second job (`nextcloud-offsite`, 04:00 daily, same paths and retention)
pushes an encrypted copy to Hetzner Object Storage, because the USB drive
shares a building with the server and would not survive fire, theft, or a
power surge. It is deliberately independent of `/mnt/backup`, so off-site
backups keep running when the drive is unplugged or dead.

Both repos use the same `restic-password` secret; the off-site one also
needs `restic-offsite-env` (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`).
The endpoint and bucket are set at the top of
`modules/core/services/restic-backup.nix`.

The repo password is the `restic-password` agenix secret — **also keep a
copy in the password manager**; without it the repo is unreadable.

If the drive is unplugged the run fails loudly (`SystemdUnitFailed`
alert); more than 3 days without a successful run fires
`ResticBackupStale`.

```sh
sudo systemctl start restic-backups-nextcloud           # manual run (blocks)
sudo systemctl start restic-backups-nextcloud-offsite   # same, off-site repo
sudo restic-nextcloud snapshots                         # wrapper, repo/password preset
sudo restic-nextcloud-offsite snapshots
```

### Restore

```sh
sudo nextcloud-restore
```

Interactive: asks which repo (local or off-site — pick off-site when the
USB drive is gone), lists snapshots, asks which to restore (default `latest`),
requires typing `restore` to confirm, then stops php-fpm/cron, restores
files with `--delete` (true point-in-time — files created after the
snapshot are removed), reloads the DB from the snapshot's dump, clears the
Redis cache, restarts services, and re-scans files. Source:
`scripts/nextcloud-restore.sh`. For a non-destructive look inside a
snapshot instead: `sudo restic-nextcloud restore latest --target /tmp/restore`.
